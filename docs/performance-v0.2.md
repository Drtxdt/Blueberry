# 0.2 Alpha：性能与交付验收

测量日期：2026-09-12；同一 Windows x64 机器、release 构建。启动增量 P50 ≤50 ms、热态菜单 P95 ≤20 ms 是验收门槛，不以 Rust 查找耗时代替端到端延迟。

**性能验收未通过。** 最终交付的 0.2.0 二进制完成了功能回归；启动增量和热态菜单仍超过门槛，不能以本次优化提交代表达标。

| 最终测量项 | 样本数 | P50（ms） | P95（ms） | 验收 |
| --- | ---: | ---: | ---: | --- |
| 首次输入配对增量，不加载 profile 的控制组 | 30 对 | 102.96 | 150.94 | 未通过 P50 ≤50 |
| 首次输入配对增量，保留实际 profile | 30 对 | 119.71 | 166.72 | 未通过 P50 ≤50 |
| 热态菜单，说明开启、应用缓存未命中 | 300 | 29.19 | 37.63 | 未通过 P95 ≤20 |
| 热态菜单，说明开启、应用缓存命中 | 300 | 30.44 | 37.60 | 未通过 P95 ≤20 |
| 热态菜单，说明关闭、应用缓存未命中 | 300 | 26.26 | 37.08 | 未通过 P95 ≤20 |

说明开启时，完整宿主的首次提示符 P50 为 566.19 / 554.27 ms，首次菜单 P50 为 84.80 / 86.59 ms，Rust 宿主菜单时 working set P50 为 9.54 / 9.31 MiB（依次为应用缓存未命中 / 命中）。首次提示符不等同于输入已就绪。

本批说明开启相对关闭，热态 P50 高 2.93 / 3.15 ms，P95 高 0.55 / 1.49 ms。这是顺序批次的观测差值，尚不足以把差异全部归因于中文说明，也不能声称说明没有性能成本。

相对补全修复基线，最终版本的无 profile 首次输入增量 P50 从 120.70 降至 102.96 ms，实际 profile 从 78.34 升至 119.71 ms；说明开启的热态 P95 从 37.30 / 37.07 变为 37.63 / 37.60 ms。后者没有改善，启动也没有跨 profile 的稳定改善。中间性能提交曾得到更低的尾延迟，但最终验收使用包含全部功能的交付二进制，保留这些回退结果。

## 方法与原始数据

- [最终 adapter](benchmarks/v0.2-final-adapter.json)：30 对全新 pwsh/ConPTY 会话，基准与适配会话交替先后顺序，不加载 profile。
- [保留用户 profile](benchmarks/v0.2-final-profile.json)：同样 30 对，双方均保留实际 profile 和原提示符；测试关闭历史写入，不修改 profile。
- [说明开启](benchmarks/v0.2-final-host.json) / [说明关闭](benchmarks/v0.2-final-host-no-descriptions.json)：每种说明设置均测 30 次应用缓存未命中与 30 次命中；每次启动后修改前缀 10 次，即每种缓存状态 300 次热态菜单。
- 完整宿主固定配置、临时 fixture 目录，使用同一 release 和相同 PATH 构造。cache hit 在采样前验证完整缓存与子进程 PATH/PATHEXT，结束后检查缓存未被重复写入。
- 正式计时关闭 trace；不清空 OS 文件缓存，不隔离 CPU 频率和系统后台负载。两种说明设置按批次顺序测量，不能把毫秒级差异直接视为因果效果。
- 中位数是偶数样本中间两项均值；P95 为 nearest-rank。各阶段的中位数不可相加。保留旧原始样本及 [重算 adapter](benchmarks/v0.1-adapter-recomputed.json)、[重算 host](benchmarks/v0.1-host-recomputed.json)。

“首次提示符”是可见文本出现时间；“首次输入”需看到输入回显；“菜单”需同时看到对应的可编辑前缀及区分不同查询的候选。完整宿主经过外层测试 ConPTY 和宿主内层 ConPTY，包含两层输出开销，不能等同于 Windows Terminal 实际帧呈现时间。working set 只统计 Rust 进程，不含 pwsh/ConHost/Windows Terminal。

热态数字来自固定的首词候选 fixture；它验证同一渲染与传输链路，不代表所有 Git 参数列表、大目录、多行输入和自定义 profile 的尾延迟。

## 修复基线与性能取舍

[分阶段报告](benchmarks/v0.2-perf-summary.md) 保留补全修复后的基线和性能提交数据。未在相同条件下测量原 inshellisense，不给出相对它的加速倍数。

已实施：System.Text.Json、PSReadLine 直接 API、后台分批索引、独立缓存写入、cache hit 不写盘、重复查询不重建索引、相同菜单不重绘、合并已有输入事件，以及每批终端输出集中写出。候选总量未缩减，普通启动仍加载用户 profile。

**尚未完成的性能事项：首个 shell 命令快照没有完全退出首次查询关键路径。** 为保持当前会话的 alias/function 一致性，快照在同一 PSReadLine runspace 同步物化；后续以 128 条分页交错处理查询。首个采集仍可能阻塞已经排队的输入。独立 adapter probe 不含该枚举，完整宿主首次菜单包含它；不把两者混为同一指标。

诊断 trace 用于拆分阶段，不用于验收：[未命中](benchmarks/v0.2-trace/miss-0.jsonl) 和 [命中](benchmarks/v0.2-trace/hit-0.jsonl) 各一次独立会话中，适配初始化约 110–111 ms（其中 PSReadLine 初始化约 47 ms），首次会话命令快照约 44–45 ms。两次会话内 Rust 补全单次最大 0.153 ms，重绘最大 0.149 ms，输出写入最大 0.279 ms；这些最大值不是 P95，也不包含终端实际呈现。首个查询往返可达 64–79 ms。

下一步应针对 PowerShell 首次 JIT/初始化、首个会话快照和 ConPTY 输出链路验证优化，而不是只继续缩短静态查找。不得通过等待首次输入才初始化、关闭用户 profile 或缩减候选制造改善。
