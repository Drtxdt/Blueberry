# 首次性能验收：Windows x64

测量时间：2026-09-11，release 构建。CPU 为 Intel Core i9-13900HX，32 个逻辑处理器；Windows build 26200；pwsh 7.6.6、PSReadLine 2.4.5、Rust 1.94.1。

本轮交付是可运行 Alpha。**启动增量和菜单延迟尚未达到目标，不能宣称 Rust 重写已全面提速。** 未在相同条件下测量原 inshellisense，因此也不提供相对它的加速倍数。

## 结果

| 指标 | P50 | P95 |
| --- | ---: | ---: |
| 基准 pwsh 首次输入回显 | 417.4 ms | 456.1 ms |
| 带适配脚本的 pwsh 首次输入回显 | 536.4 ms | 570.2 ms |
| 配对的适配增量 | **119.4 ms** | 159.0 ms |
| 完整 Rust 宿主首次可见提示符 | 545.7 ms | 561.3 ms |
| 完整宿主首次菜单 | 82.7 ms | 99.5 ms |
| 完整宿主热态菜单 | **25.2 ms** | 38.4 ms |
| PSReadLine 缓冲区查询往返 | 0.661 ms | 1.801 ms |
| Rust 首词查找 | 0.062 ms | 0.111 ms |
| 宿主自身 working set，菜单出现后 | 9.45 MiB | 9.63 MiB |

本机 PATH 索引有 1,738 个命令，一次构建耗时 14.19 ms。可执行文件为 2,054,656 字节（约 1.96 MiB），不包含系统已有的 pwsh/.NET。

## 测量方法与限制

- [适配原始数据](benchmarks/adapter-windows-x64.json)：10 对新建 pwsh/ConPTY 会话，交替运行顺序；每个适配会话查询 10 次，索引查找共 100 次。
- [完整宿主原始数据](benchmarks/host-windows-x64.json)：10 个新建宿主，通过外层 ConPTY 启动，宿主内再启动 pwsh。每个会话测一次首次菜单和一次修改前缀后的菜单。
- 两组使用 no-profile；基准和适配会话均设置 UTF-8 并关闭历史写入。完整宿主用固定配置、临时命令和独立数据目录，包含首次索引成本。
- 不清空 OS 文件缓存、不隔离 CPU 频率或系统后台负载。完整宿主指标包含测试所用的两层 ConPTY，不能等同于 Windows Terminal 中的帧呈现时间。
- JSON 字段 `median` 使用排序后的上中位数作为 P50；P95 使用 nearest-rank。在 10 个样本中 P95 就是最大样本，样本量不足以估计稳定尾延迟。
- working set 仅统计 Rust 宿主进程，排除 pwsh、ConHost、Windows Terminal；不是总内存或 private bytes。不能相加不同测量阶段的 P50，也不能把查找时间当作按键到显示的总延迟。

## 后续工作，保持 2 > 3 > 4 > 1

1. **启动**：当前约 119 ms 的适配增量没有通过 ≤50 ms 的初始目标。下一步分别测脚本解析、模块导入、首次 JIT、协议序列化和首个命令快照；优先缩短首个可输入提示符前的工作。基准自身已有约 417 ms，不应把 pwsh 的所有启动成本归因于补全器。
2. **首词与交互**：首词功能已打通，但热态菜单 P95 约 38 ms，尚未达到 ≤20 ms 的目标。下一步用时间戳拆解输入、查询、后台查找、ConPTY 输出和重绘，避免在仅 0.062 ms 的查找上盲目优化。再补齐动态 Git 数据、模块变更通知与更复杂语法。
3. **个性化**：TOML 颜色、边框、图标、描述及配置重载已实现；继续扩展预设主题和不同终端背景的可读性。
4. **Node 兼容**：新程序运行与构建均不依赖 Node，避开其 ABI/编译链问题；没有修改或修复原 inshellisense 的 Node 22 构建。

运行时继续保持 Rust 核心 + PowerShell 接入脚本。是否引入极小的托管桥接层，应由相同测试下的实际收益决定，不以语言比例代替性能验收。
