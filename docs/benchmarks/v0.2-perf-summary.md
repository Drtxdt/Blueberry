# 补全修复后的性能对照

2026-09-12，同一 Windows x64 机器、release 构建。每组启动交替测 30 对 baseline/adapter；完整宿主每种应用缓存状态 30 次启动、300 次热态菜单。正式计时关闭 trace，OS 缓存未清空。

| 指标 | 修复基线 P50 / P95（ms） | 性能提交 P50 / P95（ms） |
| --- | ---: | ---: |
| 无 profile：配对首次输入增量 | 120.70 / 152.82 | 98.77 / 141.10 |
| 保留用户 profile：配对首次输入增量 | 78.34 / 101.48 | 103.10 / 146.46 |
| 应用缓存未命中：热态菜单 | 29.17 / 37.30 | 28.15 / 31.90 |
| 应用缓存命中：热态菜单 | 29.24 / 37.07 | 28.31 / 31.80 |

启动 P50 ≤50 ms、热态菜单 P95 ≤20 ms 均未通过。无 profile 和热态菜单有改善，实际 profile 的配对增量反而增加；不能以单组改善宣称全面提速。不同批次的系统负载未隔离，后续仍需复测 profile/JIT 成本。

修改包括 System.Text.Json、PSReadLine 直接 API、独立缓存写入线程、查询之间复用索引、相同菜单不重绘，以及合并已有输入事件和每批输出。未缩减候选，正常启动仍加载用户 profile。

首个 shell 快照仍在 PSReadLine 的同一 runspace 内同步采集，可能阻塞已经排队的首次输入。128 条分页只允许后续查询穿插；尚未实现完全退出首个查询关键路径。独立 adapter probe 的启动增量不含该枚举，完整宿主首次菜单包含它。

初轮诊断 trace 显示 Rust 查找、菜单生成和写出分别在亚毫秒级，首个 shell 快照约 41 ms；热态可见菜单还经过 PSReadLine 和内外两层 ConPTY 的输出。trace 会增加开销，仅用来定位，不能作为性能验收样本。

原始数据：同目录下的 `v0.2-fixes-{adapter,profile,host}.json` 与 `v0.2-perf-{adapter,profile,host}.json`。统计统一使用偶数样本中间两项均值作为中位数，P95 为 nearest-rank。旧原始样本保留，修正统计在 `v0.1-*-recomputed.json`。
