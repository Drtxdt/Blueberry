# 第二轮复审：补全与启动归因

基线为公开 v0.5.3 的包内源码 `8b97ebbc`，被复审的产品源码为 `9d88a944`，本轮起点为 `43407bb`。以下正式数字来自[已封存的跨版本回执](review-hardening-remote-validation.json)，不是新候选的验收成绩。

## 目录无法读取

`PathCache::complete_with_mode` 遇到文件冒充目录或拒绝网络路径时，返回终态诊断。原来的 `completion::merge` 只转发“未完成且未扫描”的来源诊断。修复后，`sources::collect_lane` 明确标出要展示的消息，错误行不产生可接受的编辑，也不会留下同次查询中已被删除的旧候选。普通项目来源说明仍留在来源状态里。

回归 `unavailable_path_renders_a_final_status_without_retaining_an_old_edit` 修复前得到零行，修复后能看到两类提示；`unmatched_editor_manual_completion_preserves_native_editing` 用真实 PowerShell 注册参数补全器，验证错误行出现后 Tab 仍能填入原生候选。

## 360 对原始样本究竟慢在哪里

从每个 Actions 工件读取经 SHA-256 校验的 `summary.json`，先对**同一样本**计算“完整静态菜单到达 − 首个静态候选到达”，再逐对比较。下表是这个区间的毫秒数；每格依次为**发布版 P50 / 受审版 P50 / 逐对差值 P50**。每组 30 对，独立 runner、缓存状态与批次均未混合。

| --- | ---: | ---: | ---: | ---: |
| PS5.1 / 2.0.0 | 0.23 / 48.62 / +46.93 | 0.21 / 45.60 / +45.38 | 0.23 / 121.51 / +121.29 | 0.22 / 124.01 / +123.80 |
| PS5.1 / 2.4.5 | 0.26 / 49.33 / +48.96 | 0.32 / 48.84 / +48.49 | 0.31 / 117.13 / +116.73 | 0.31 / 116.61 / +116.19 |
| PS7 / 2.4.5 | 0.36 / 87.84 / +87.45 | 0.40 / 87.99 / +87.24 | 0.37 / 274.01 / +273.59 | 0.42 / 266.51 / +266.06 |

复算：`python scripts/analyze-static-readiness.py artifacts/review-hardening/remote-41648304986`。输入是三份原始 ZIP；测试防止错位样本与反向时间戳被纳入计算。

**能确认的事实：** 两侧均由同一探针观测带候选的完整状态栏。发布版在启动子进程后即用父环境扫描，菜单使用 `Completion.incomplete`；受审版等待权威子环境，状态栏使用 `Completion.pending`。探针的“完整”指屏幕上的状态栏不再显示加载，不等价于索引扫描刚刚结束。冷暖区分的是系统命令元数据，PATH 索引在每一对中都从新数据目录开始。因此既不能把这张表当作目录扫描耗时，也不能把它当作首个提示符增量。

**诊断边界：** 在 `direct::run` 记录子环境发布、接收与 PATH/PATHEXT 相对父进程的差异（仅两个标志位）；在 `Worker::new` 区分缓存验证命中、未命中和强制刷新，记录准备、每批枚举、快照、批间工作及最终完整或带错误的结束状态。批间时间包含查询、发布和调度，不能直接当成 CPU 调度等待。保留原有权威环境、代际取消和缓存验证路径。历史正式样本未开追踪，不能把这些历史差值全部归因给任何单一阶段。

## 同机归因与三种启动入口

[11 月 11 日本机诊断回执](review-round2-local.json)记录每份报告和原始追踪的 SHA-256。使用 PS7 7.6.9 / PSReadLine 2.4.5、同一观察器、同一份复制的 PSHOME、相同父 PATH/PATHEXT、原生编辑器 DLL、观察尺寸和电源策略。每次均验证系统元数据缓存命中，PATH 缓存从空目录开始。第一次用机器默认 PATH 的探针因系统账户目录不可读，屏幕实际显示目录错误，未取得完整菜单；该次没有计入任何比较。重测只从测试进程的 PATH 移除了这个目录，未修改用户环境。

**冻结版本对照。** 在专用入口以“公开 → 受审 / 受审 → 公开”顺序运行两对带追踪的诊断。公开包在宿主时间 36.5 / 44.4 ms 完成 PATH 扫描，两次都早于编辑器握手（668.4 / 619.9 ms）；首候选至完整状态栏仅 0.017 / 0.025 ms。受审包的首个扫描批次在 739.5 / 756.0 ms，末批在 895.0 / 909.6 ms，首候选至完整状态栏为 150.5 / 146.1 ms。两个包的私有编辑器 DLL 随各自的产品版本变化，原生对照 DLL 相同。这直接观察到了扫描与初始化重叠方式的改变，不能据此单独解释历史 CI 每一组的差值。

**新候选内部。** 四份暖缓存追踪中，父子 PATH/PATHEXT 均相同。worker 在权威环境到达后 0.03–0.10 ms 开始，约 156–161 ms 后完成。每次共 37 批：实际枚举累计 13.7–14.6 ms、快照约 2.2–2.4 ms；批间累计 132.9–136.9 ms，其中包含正在显示的查询的 33 次重新规划，规划累计 59.6–62.3 ms。这些嵌套时间不能相加。完整状态栏在索引结束后 6.3–8.6 ms 到达。若要进一步优化，已有证据支持先单独实验“首帧之后是否每一批都需要重算同一查询”，同时保留输入响应和权威子环境约束。

**原生 / 专用 / 自动 Profile。** 下表为同机**关闭追踪**的两对诊断，单位 ms。每个入口都有自己的原生对照；终点为首个真实按键回显。专用入口使用 Windows Terminal fragment 对应的 EXE 启动方式；通过 ConPTY 观察，不包括真实 WT 创建窗口的时间。

| 顺序 | 自动 Profile / 其原生对照 | 专用入口 / 其原生对照 | 自动减专用 |
| --- | ---: | ---: | ---: |
| 自动 → 专用 | 2290.74 / 1802.12 | 1773.07 / 1756.91 | 517.67 |
| 专用 → 自动 | 2252.63 / 1786.65 | 1776.20 / 1772.45 | 476.43 |

另两对开启追踪的样本仅用于拆解：运行前维护耗时 0.01–0.04 ms，子进程创建调用耗时 7.2–15.8 ms，从该调用返回到子 Shell 进入 bootstrap 为 607.6–677.9 ms，bootstrap 入口到 PSReadLine 模块就绪为 6.5–7.9 ms。此处的“模块就绪”不等于所有编辑器初始化完成。观察器的启动起点包含 ConPTY 的准备，不能把它至 Rust 入口的全部时长都记到 Blueberry。没有改变默认启动方式，也不足以宣布启动增量 P50 ≤50 ms。

复现：用 `scripts/prepare-profile-entry.ps1` 将同一 PS7 复制到新的隔离目录，并固定原生编辑器。运行 `python scripts/measure-startup-entries.py --shell <复制的 pwsh.exe> --executable <候选 EXE> --fixture <blueberry-profile-probe.json> --output <新目录> --pairs 2 --cache warm`；另选新目录加 `--trace` 获取诊断。脚本拒绝身份变化、缺失阶段及不属于本次启动的追踪。在一次性 Windows CI 账户上，`test-ci-profile-entry.ps1 -CompareEntries` 对三种编辑器执行相同对照。历史版本诊断使用同一观察器的 `product-probe --host-executable <受测包内 EXE>`，原始目录及身份见回执。

## 真实 Windows Terminal 的人工验收（待执行）

在官方 Windows Terminal 的新标签页，从仓库运行 `./scripts/check-wt-menu.ps1`。它使用隔离临时目录、候选 EXE、无 Profile 的子 Shell 和 F6 手动触发，不安装 Profile。保留屏幕截图、WT 版本、行列数和脚本输出的追踪目录。

1. 输入 `Get-ChildItem .\many\absent`，按 F6。观察“正在加载…”到“没有匹配的候选”的过渡；如果扫描太快未看清加载，单独记录“未观察到”。按普通字符后输入应继续。
2. 输入 `Get-ChildItem .\blocked\中文`，按 F6。应只看到目录错误，不应出现可选行；Esc 后原生光标和行内容应还在。
3. 在窄窗口和缩放后的窗口重复。在子 Shell 内执行 `function prompt { ('长提示符' * 12) + '> ' }`，用中文输入法组词、选字，在窗口底部触发和关闭菜单；核对换行、叠盖以及关闭后原有文本是否恢复。

ConPTY 的 Tab 验证、渲染单测和本表的帧时序不能替代上述人工结果。

## 包身份与合并条件

本地候选为 **0.5.4（未发布）**，受测 Release 二进制来自干净的 `281738d`，ZIP 与全部 28 个载荷的哈希已核验，详见[本地回执](review-round2-local.json)。`scripts/test-release.ps1` 使用公开 0.5.3 的 EXE 和新候选，在临时安装根通过安装、升级、回滚与卸载检查。公开 v0.5.3 的发布记录和附件保持原样，旧版的性能与用户试用豁免不适用于 0.5.4。

工作流先跑 quick，再跑跨平台核心、Windows PowerShell、PS7、原生鼠标和打包。来自 `codex/review-hardening` 的 PR 还要求修正过的稳定性和正式 AB/BA 工作流通过，入口诊断单独上传。供分支保护选择的汇总检查名是 **PR acceptance**；工作流定义本身不能设置仓库端的保护规则。11 月 11 日本地另对两项历史场景各跑了开启和关闭追踪各一次，共四次通过。这既不是新的远程全绿回执，也没有给历史故障结案。
